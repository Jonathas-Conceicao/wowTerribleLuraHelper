# Phase 3 — UI Design Contract

> Visual and interaction contract for the TerribleLuraHelper Settings panel and its
> integration touch-points with the Phase 2 helper window.
> This is a WoW Midnight (Interface 120005) Lua addon. The "UI" delivered in this phase
> is **the native Blizzard Settings panel** under Options > AddOns. Blizzard owns all
> typography, spacing, color, chrome, layout primitives, focus states, and accessibility.
> The addon does NOT style the panel — every visual decision below is either inherited
> from `wow-ui-source@12.0.1.66337` or is a string the addon supplies to a Blizzard widget.
>
> The standard 6 design dimensions reduce to: copywriting (labels and tooltips) and
> design system (Blizzard's Settings panel = the system). Sections that do not apply to
> a native-panel context are explicitly marked **N/A** with the reason, rather than fabricated.
>
> Generated by gsd-ui-researcher. Verified by gsd-ui-checker.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none (Blizzard native Settings API) |
| Preset | not applicable |
| Component library | Blizzard `Settings.*` API (`wow-ui-source\Interface\AddOns\Blizzard_Settings_Shared\`) |
| Layout container | `Settings.RegisterVerticalLayoutCategory("TerribleLuraHelper")` — vertical stack only, no column/grid primitive available to addons (SETTINGS_API.md §10) |
| Category placement | `Settings.RegisterAddOnCategory(category)` → Options > AddOns subtree |
| Setting binding | `Settings.RegisterAddOnSetting` — auto-defaults the SavedVariables key on registration AND writes new values back on every change (no addon-side DB writes from change callbacks) |
| Icon library | not applicable — all controls are text-labelled Blizzard widgets |
| Font | inherited from Blizzard Settings panel; addon never sets a font |

**Out of scope for this phase:**
- Panel styling (Blizzard owns the chrome — addon cannot and must not theme it)
- Helper-window restyling (Phase 2 visual contract is locked; AMEND-04..08 in Phase 2 verification frontmatter are authoritative)
- Schema migration (CONTEXT.md D-33/D-34 — all Phase 3 setting keys already exist in `TerribleLuraHelperDB`; no new fields)

The panel is a single vertical stack. Sections are rendered top-to-bottom in the order shown.
Each section starts with `CreateSettingsListSectionHeaderInitializer(name)` and is followed by
its controls in registration order. Per CONTEXT.md D-06..D-09:

|---|------------------------------|--------------------------|
| 1 | `Chat channels` | 6 channel checkboxes (D-06) |

No section dividers, no spacers, no two-column layouts — Blizzard's vertical layout has no such primitive (SETTINGS_API.md footgun §10). Visual rhythm is whatever the Settings panel renders by default for adjacent initializers.

## 2. Section 1: Chat Channels

### 2.1 Layout

`layout:AddInitializer(CreateSettingsListSectionHeaderInitializer("Chat channels"))` followed by 6 calls to `Settings.CreateCheckbox(category, setting, tooltip)` in the order below.

### 2.2 Checkbox table — final labels and tooltips

| Order | DB key | UI label | Default | Tooltip |
|-------|--------|---------|---------|---------|
| 1 | `SAY` | `Listen on /say` | `true` | `Watch /say messages for raid markers.` |
| 2 | `RAID` | `Listen on /raid` | `true` | `Watch /raid messages for raid markers.` |
| 3 | `RAID_LEADER` | `Listen on /raid (leader)` | `true` | `Watch raid-leader messages for raid markers.` |

| 5 | `INSTANCE_CHAT` | `Listen on /instance` | `true` | `Watch /instance messages for raid markers.` |
| 6 | `INSTANCE_CHAT_LEADER` | `Listen on /instance (leader)` | `true` | `Watch instance-leader messages for raid markers.` |

**`variable` (unique global identifier) prefix:** `TLH_CHANNEL_<KEY>` per SETTINGS_API.md §1 (e.g. `TLH_CHANNEL_SAY`).

### 2.3 Interaction contract

- Toggle is **live**. `setting:SetValueChangedCallback` fires immediately on click (no Apply button), framework writes `db.listenChannels[KEY] = value`, and the next `CHAT_MSG_*` arrival reads the flag at `Window.lua:276`.
- Channel-toggle change callback is a **no-op** for chat-event registration (CONTEXT.md D-12). The chat-event handler stays registered for all 6 events whenever the window is shown (Phase 2 AMEND-01 visibility-gated registration); per-channel filtering happens at message-time. Therefore the Phase 3 callback body is `function(_, value) end` — purely cosmetic; the `Settings.RegisterAddOnSetting` framework writes through automatically.
- Combat: unrestricted. Toggling during combat works (no protected API touched).

## 3. Section 2: Window

### 3.1 Layout

`layout:AddInitializer(CreateSettingsListSectionHeaderInitializer("Window"))` followed by, in this order:
1. Scale slider
2. Alpha slider
3. `Auto-hide when empty` checkbox

### 3.2 Scale slider (CFG-04, WIN-08)

| Property | Value |
|----------|-------|
| `variable` | `TLH_WINDOW_SCALE` |
| `variableKey` | `scale` (in `db.window`) |
| `variableTbl` | `db.window` |
| Variable type | `Settings.VarType.Number` |
| UI label | `Window scale` |
| Default | `1.00` |
| Min | `0.50` |
| Max | `2.00` |
| Step | `0.05` |
| Right-side label | percentage via `MinimalSliderWithSteppersMixin.Label.Right` + `FormatPercentage` |
| Tooltip | `Resizes the helper window. Drag to preview live.` |
| Live update | YES — drag updates `ns.win:SetScale(value)` immediately |

Implementation handle: callback calls `ns:SetWindowScale(value)`, exported from `Window.lua` per CONTEXT.md D-17. Body: `if ns.win then ns.win:SetScale(v) end` (already established in SETTINGS_API.md §2).

### 3.3 Alpha slider (CFG-10, WIN-10)

| Property | Value |
|----------|-------|
| `variable` | `TLH_WINDOW_ALPHA` |
| `variableKey` | `alpha` (in `db.window`) |
| `variableTbl` | `db.window` |
| Variable type | `Settings.VarType.Number` |
| UI label | `Window opacity` |
| Default | `1.00` |
| Min | `0.20` |
| Max | `1.00` |
| Step | `0.05` |
| Right-side label | percentage via `MinimalSliderWithSteppersMixin.Label.Right` + `FormatPercentage` |
| Tooltip | `Adjusts the helper window's transparency. Has no effect while auto-hide has hidden the window.` |
| Live update | YES — but conditional on soft-hide state (see §3.5) |

**Min of 0.20** (not 0.0): below 0.20 the window becomes effectively invisible, which collides with auto-hide's `alpha=0` state and would confuse users into thinking the addon is broken. 0.20 keeps the lowest setting still perceptible. (Matches existing Phase 2 default-spec range.)

Implementation handle: callback calls `ns:SetWindowAlpha(value)`. Per CONTEXT.md D-21: when `softHidden=true`, the callback updates `db.window.alpha` (framework does this) but does NOT call `win:SetAlpha(value)` — the soft-hide override (alpha=0) wins. The new alpha applies the next time soft-hide exits.

### 3.4 Auto-hide checkbox (CFG-05)

| Property | Value |
|----------|-------|
| `variable` | `TLH_AUTO_HIDE` |
| `variableKey` | `autoHide` (in `db.window`) |
| `variableTbl` | `db.window` |
| Variable type | `Settings.VarType.Boolean` |
| UI label | `Auto-hide when empty` |
| Default | `false` |
| Tooltip | `When enabled, the helper window stays visible but invisible while no runes are showing. The next message reveals it.` |
| Live update | YES — toggling triggers `applySoftHideState()` immediately |

Tooltip wording rationale: the user-facing model is "the window stays around but is invisible until needed." Saying "hides while empty" is technically wrong for the soft-hide implementation (`win:IsShown()` still returns true; chat events stay registered; mouse events still hit the now-invisible frame). The phrasing "stays visible but invisible" foregrounds that distinction without exposing implementation jargon. Keeps the user from being surprised when their cursor accidentally clicks "nothing" and lands on the still-mouseable frame.

Implementation handle: callback calls `ns:OnAutoHideChanged(value)` which calls `applySoftHideState()` per CONTEXT.md D-22.

### 3.5 Soft-hide visual contract (D-18..D-22)

This is the one place in Phase 3 where the addon's visual behavior is non-trivial. Lock the contract here so the executor and ui-checker have a single source of truth.

**Soft-hide state:** `softHidden = true` (Lua local in `Window.lua`).

| Aspect | Behavior |
|--------|----------|
| `win:IsShown()` | Returns `true` (frame is NOT hidden — only its alpha is 0) |
| `win:GetAlpha()` | Returns `0` |
| Mouse events | Still hit the frame (drag-when-unlocked still works in soft-hide; user cannot see what they're dragging) |
| Chat events | Still registered (OnShow/OnHide do not fire on alpha changes); message arrival exits soft-hide (D-19) |
| Slot widgets | Still drawn under alpha=0 |
| Lock button | Still drawn under alpha=0 |
| 20s self-clear timer | Still fires; on fire, re-enters soft-hide if `autoHide=on` |

**Soft-hide enters when:** `db.window.autoHide == true` AND `#sequence == 0`. Sets `softHidden=true`, calls `win:SetAlpha(0)`. Hooks: end of `ClearAll`, autoHide-toggle change callback (when toggling to `true` while window shown and slots empty).

**Soft-hide exits when:** EITHER `db.window.autoHide == false` OR `#sequence > 0`. Sets `softHidden=false`, calls `win:SetAlpha(db.window.alpha)`. Hooks: end of `FillSlot` (sequence > 0 → exit), autoHide-toggle change callback (when toggling to `false` while soft-hidden), `ns:ShowWindow()` (D-20 — explicit user action always reveals the window).

**Explicit `/lura show` while `autoHide=on` and slots empty:** D-20 mandates the window becomes visible (alpha = `db.window.alpha`). The next 20s self-clear re-enters soft-hide. Rationale: visibility is a UX confirmation that the addon is engaged. Without it, `/lura show` while auto-hide is on looks like nothing happened.

**Mouse-pass-through caveat:** Documented but not mitigated in v1. If a future user reports accidental clicks on the invisible frame, v1.1 can add `win:EnableMouse(false)` while soft-hidden and re-enable on exit. Defer.

## 4. Section 3: Actions

### 4.1 Layout

`layout:AddInitializer(CreateSettingsListSectionHeaderInitializer("Actions"))` followed by two `CreateSettingsButtonInitializer` calls (per SETTINGS_API.md §4 signature: `name, buttonText, onClick, tooltip, addSearchTags`).

### 4.2 Recreate Macros button (CFG-06, MACR-04)

| Property | Value |
|----------|-------|
| `name` (left-side label) | `Macros` |
| `buttonText` (button face) | `Recreate / update macros` |
| `tooltip` | `Recreates or updates the five TLH_* player macros — adds them if missing, refreshes the body if you've edited them. Disabled during combat — the addon retries automatically when combat ends.` |
| `addSearchTags` | `true` |

**OnClick contract (CONTEXT.md D-23):**

```
1. If InCombatLockdown() is true:
   print "|cffaa44ffTLH|r: Can't recreate macros during combat.
          They will be retried on PLAYER_REGEN_ENABLED, or click again after combat."
   return.
2. Otherwise call ns:RegisterMacros() (Macros.lua:32 — already exported).
3. Print "|cffaa44ffTLH|r: Macros recreated." (always, regardless of the
   macrosPrintedThisSession flag in Macros.lua — explicit user action confirms).
```

**Why bypass `macrosPrintedThisSession`:** the Lua-local flag in `Macros.lua:24` suppresses the auto-registration hint after first session-print. An explicit user click on "Recreate macros" should always confirm, otherwise the user has no feedback that the click did anything. The print lives in `Config.lua`'s OnClick (not in `Macros.lua`), so the once-per-session flag is untouched.

**Combat-blocked notice copy (literal):**
```
|cffaa44ffTLH|r: Can't recreate macros during combat. They will be retried on PLAYER_REGEN_ENABLED, or click again after combat.
```

**Success notice copy (literal):**
```
|cffaa44ffTLH|r: Macros recreated.
```

Color codes match Phase 2's chat-output convention (`|cffaa44ff` purple-violet TLH prefix, `|r` reset).

### 4.3 Lock/Unlock window button (CFG-07, D-24)

| Property | Value |
|----------|-------|
| `name` (left-side label) | `Window` |
| `buttonText` | **dynamic function** (see below) |
| `tooltip` | `Toggles whether the helper window can be dragged.` |
| `addSearchTags` | `true` |

**`buttonText` function body:**
```lua
local function buttonText()
    if ns.db.window.locked then
        return "Unlock window"   -- currently locked → button offers to unlock
    else
        return "Lock window"     -- currently unlocked → button offers to lock
    end
end
```

Wording rationale: the button describes the **action it performs**, not the current state. "Unlock window" means clicking it unlocks (so the window must be currently locked). This matches the Blizzard convention used by every Settings toggle-action button.

**OnClick:** `ns:ToggleLocked()` (already exported by `Window.lua:210`). The existing `applyLockState()` (Window.lua:197) handles `SetMovable` / `RegisterForDrag` / lockBtn:Show/Hide.

**Dynamic-label re-evaluation timing (locked):** Per `wow-ui-source\Interface\AddOns\Blizzard_Settings_Shared\Blizzard_SettingControls.lua:702-720`, `EvaluateName` is called once when the button initializer runs `Init`. **Confirmed via direct source read.** This means:
- Open panel → button text correctly reflects `db.window.locked` at that moment.
- Click button in panel → `ToggleLocked` mutates `db.window.locked` BUT the button text does NOT update on this open instance (Init is not re-run on click). The button shows the OLD label until the panel reinitializes.
- Reopen panel → text refreshes correctly.

Document this as expected v1 behavior. Workaround if the label is observed staleness becomes a UX issue: re-show the panel via `Settings.OpenToCategory(ns.settingsCategoryID)` from the OnClick handler (forces reinit). **Not implemented in v1** — the slash escape hatches `/lura lock` and `/lura unlock` (D-25) make the panel button less load-bearing.

**Combat:** unrestricted. `SetMovable`/`RegisterForDrag` are non-protected APIs.


### 4.5.3 Recreate / update macros button (CFG-06, MACR-04)

Identical to the original §4.2 spec EXCEPT for `buttonText`: `"Recreate / update macros"` (was `"Recreate macros"`). Tooltip updated to convey idempotent update behavior — see §4.2 for the new wording.

The new wording communicates that the button is safe to click any time: missing macros are created, edited macros are refreshed back to the canonical body, untouched macros are no-ops at the framework level (EditMacro with identical args is a write-through).

### 4.5.4 Macro body construction (Macros.lua schema change, D-38)

Phase 3 amends `Macros.lua` so the body is built dynamically from `db.macroChannel`:

```lua
local CHANNEL_PREFIX = {
    RAID         = "/raid",
    RAID_WARNING = "/rw",
    SAY          = "/s",
}

-- The MACROS table holds rt-codes only:
local MACROS = {
    { name = "TLH_Diamond",  rt = 3, icon = 137003 },
    { name = "TLH_Triangle", rt = 4, icon = 137004 },
    { name = "TLH_Circle",   rt = 2, icon = 137002 },
    { name = "TLH_Cross",    rt = 7, icon = 137007 },
    { name = "TLH_T",        rt = 1, icon = 137001 },
}

-- At registration time, build body from current db.macroChannel:
local prefix = CHANNEL_PREFIX[ns.db.macroChannel] or "/raid"
for _, m in ipairs(MACROS) do
    local body = prefix .. " {rt" .. m.rt .. "}"
    -- ... existing CreateMacro / EditMacro path ...
end
```

This is constant-string concatenation by addon code — NOT touching `msg` from any chat event. Hard taint constraints (CLAUDE.md) are unaffected.

## 6. `/lura config` Open Path (CMD-05)

### 6.1 Behavior

`/lura config` and `/tlh config` invoke `ns:HandleSlashCommand("config")` which:

```
1. If ns.settingsCategoryID is nil:
   print "|cffaa44ffTLH|r: settings not yet ready, try again in a moment."
   return.
2. Otherwise call Settings.OpenToCategory(ns.settingsCategoryID).
```

The ID is captured once at panel registration time inside the `EventUtil.ContinueOnAddOnLoaded` block (CONTEXT.md D-03) as `ns.settingsCategoryID = category:GetID()`. ID is a **number**, not the name string — passing the name is a known footgun (SETTINGS_API.md §6).

### 6.2 Idempotence (panel already open)

If the Settings panel is already open and on the TerribleLuraHelper category, `Settings.OpenToCategory(id)` re-focuses without re-creating. If it is open on a different category, the call switches to TerribleLuraHelper. Verified path: `Settings.OpenToCategory` (`Blizzard_Settings.lua:143-145`) → `C_SettingsUtil.OpenSettingsPanel` (secure backing call). No client-side state to manage in the addon.

### 6.3 Panel scroll target

`Settings.OpenToCategory(categoryID)` opens to the top of the category (no `scrollToElementName` second arg). v1 does not deep-link to specific controls.

## 10. Empty / Error / Loading States

### 10.1 Panel registration deferred

If `EventUtil.ContinueOnAddOnLoaded` has not yet fired when `/lura config` is invoked (vanishingly unlikely — the callback is synchronous w/r/t `ADDON_LOADED`), the slash dispatcher prints:

```
|cffaa44ffTLH|r: settings not yet ready, try again in a moment.
```

No empty-state visual in the panel itself. Blizzard renders the panel skeleton; controls populate as `Settings.RegisterAddOnSetting` calls run during the `ContinueOnAddOnLoaded` body.

### 10.2 First-time-user state

No first-run dialog, no welcome card, no intro tour. Defaults are sensible (channels all on, scale 1.00, alpha 1.00, autoHide off, unlocked). The Phase 1 load banner `|cffaa44ffTerribleLuraHelper|r loaded.` plus the Phase 2 macro hint `|cffaa44ffTLH|r macros: N created, N updated. Open /macro and drag them to your action bar.` are the only first-run messages.

### 10.3 Settings panel close

`Settings.OpenToCategory` does not auto-close on focus loss. User closes the panel via Esc or the Settings frame's own close button (Blizzard chrome). No addon-side hook needed.

## UI-SPEC COMPLETE

### Visual Contract Summary

This design contract specifies the Phase 3 Settings panel as a vertical-layout category
registered under Options > AddOns, comprising 4 sections in fixed order: Chat channels
(6 checkboxes bound to `db.listenChannels`), Window (Scale slider 0.50–2.00, Alpha
slider 0.20–1.00, Auto-hide checkbox), Actions (Recreate Macros button with
combat-deferral notice, Lock/Unlock window button with state-dependent label), and Slash
commands (8 sub-headers, one per command). All controls are Blizzard-native widgets;
the addon supplies only labels, tooltips, and OnClick callbacks. Live-update is the
default for every persisted setting. The only non-trivial visual behavior is auto-hide's
soft-hide model: the helper window stays "shown" with `alpha=0` while empty, exits soft-hide
when slot 1 fills or auto-hide is disabled. The Recreate Macros button is the sole
combat-restricted control; all other interactions work in combat. `/lura config`
opens the panel via `Settings.OpenToCategory(ns.settingsCategoryID)` where the ID is
captured at registration time. The 8-command help table is the canonical source of truth
for both the panel block and `ns:PrintHelp()`.
